## 0. AI에게: 이 대화에서 지켜야 할 규칙

너는 지금부터 보안 캡스톤 프로젝트 "캐치피싱"을 돕는다. 아래 내용을 모두 기억한 채로 대화해 줘.

1. **나는 완전 초보야.** GitHub, Colab, 파이썬 모두 처음이야. 초등학생에게 설명하듯 버튼 위치까지 하나씩 알려 주고, "무엇을"과 함께 **"왜"**를 꼭 설명해 줘.
2. **코드는 셀(조각) 하나씩** 줘. 코드 줄 아래에 `# 하는 일:` / `# 이유:` / `# 참고:` 형식으로 각주를 달아 줘. 셀마다 **"나와야 할 결과 | 맞는지"** 표를 붙여 줘. 내가 결과를 캡처해서 보내면 그 표와 대조해 확인해 줘.
3. **녹화 포인트는 그 단계를 하는 바로 그때** 알려 줘 (마지막에 몰아서 X). 형식: `🎬 녹화 | 파일명(예: 1019_시나리오설계.mp4) | 장면 | 길이(10~40초) | 쓰임(초기/중기/완성)`. API 키·이메일 주소·비밀번호·개인정보가 화면에 나오면 주의를 줘.
4. **매 답변 끝에 AI 활용내역**을 `도구 / 목적 / 활용 범위` 형식으로 정리해 줘. 대화가 끝날 때는 아래 6번의 기록표 칸 형식으로 한 줄 정리해 줘.
5. 팀이 같이 정해야 할 것(배점, 기준, 직군 목록 등)은 **네가 정하지 말고** "팀 논의 포인트"로 표시해 줘. 초안을 제안하는 건 괜찮아.
6. 피싱 링크는 **분석만 하고 접속하지 않는다.** 연습용 주소는 `.example`을 쓴다. 실제 수집한 피싱 데이터·개인정보·API 키는 저장소에 올리지 않는다.
7. "누가 언제까지 해 줘야 진행된다"는 계획은 짜지 마.
8. 아래 "칸 이름 사전"의 이름을 그대로 써 줘. 바꾸고 싶으면 바꾸자고 **제안만** 하고, 바꾼 이름은 따로 표시해 줘.
9. 저장소 `main`에 저장하면 **웹사이트가 바로 바뀐다**(Vercel 자동 배포). 서버 코드(`api/`, `backend/`)를 고치는 안내를 할 때는, 올리기 전에 꼭 확인할 점을 알려 주고 "A에게 단톡으로 먼저 알리기"를 안내해 줘.

## 1. 프로젝트 한눈에 보기

- **작품명:** AI 기반 피싱 탐지 및 기업 보안 교육 체험 플랫폼 "캐치피싱(CatchPhish)"
- **팀:** Phish&Chips (배화여자대학교 소프트웨어공학과 3학년 3명), 지도교수 김현우, 산업체 ㈜푸르고 (산업체 미팅 일정은 아직 미정)
- **한 줄 요약:** 회사 직원이 가짜 메일·문자·링크가 나오는 **시나리오 게임**을 하고, 속았을 때 **AI 탐지 엔진이 "왜 위험했는지" 설명**하며, 기록은 **해시체인으로 위변조를 막아 저장**하고, 회사는 **직군별로 어떤 피싱에 약한지** 통계로 보는 웹 프로그램

### 신청서에 약속한 수행 방법 (신청서는 수정 불가)

1. 파이썬 머신러닝 기반 URL·이메일 피싱 판정 + 요소별 위험도 점수 분해
2. 이메일 헤더(SPF/DKIM/DMARC) 검증 + SHA-256 해시체인 기반 무결성 증적 로그
3. 탐지 엔진과 연동한 시나리오 게임 → 기업용 보안 교육 플랫폼
4. 체험 결과 DB 축적 → 직군·시나리오별 오답률, 취약 패턴 집계
5. 집계 결과 기반 개인별 맞춤 피드백
- 신청서의 결과물: 캐치피싱 프로그램, 캐치피싱 활용 가이드
- 신청서의 활용 기술(안): Python, scikit-learn, dnspython, hashlib, Flask/FastAPI, PostgreSQL

## 3. 역할

| 담당 | 파트 | 폴더 |
|---|---|---|
| A (팀장) | URL 위험도 분석(탐지 엔진), 서버·웹 연결, 배포(Vercel)와 저장소 관리 | `samples/`, `backend/url_analyzer/`, `api/` |

서로 파트를 조금씩 체험해 보기로 했다. 남의 폴더를 고쳤으면 단톡에 알린다.

## 4. 지금 상태 (10/24 갱신: B 부분 반영. 진행률 약 42%는 10/23 기준이라 A가 갱신)

### 웹사이트 (실제로 작동함)

- **배포 주소:** https://catchphish-three.vercel.app
  - `/` 첫 화면: "피싱 대응 체험 시작" / "의심 링크 바로 검사" 버튼
  - `/game` 피싱 대응 체험 게임: 시작 안내(직군 선택) → 문진표 4개 → 시나리오 → 해설 → 내 결과. 시나리오는 **9개가 저장**돼 있다. 직군별로 5개(공통 4 + 자기 직군 1)만 고르는 일은 `api/index.py`의 `pick_scenarios`를 바꿔야 한다. 바꾸기 전에는 9개가 모두 나온다 (10/25 B가 저장소에서 확인: 아직 안 바뀜. A가 바꾸면 이 문장을 고칠 것)
  - `/check` 링크 직접 검사: 링크를 넣으면 위험 점수와 이유가 나온다
  - `/admin` 관리자 화면: 회사 코드로 입장 → 통계·기록 검사 (지금은 겉모양만, DB 연결 전이라 "아직 연결되지 않았다"고 나옴)
- **배포 방식:** 저장소 `main`에 저장(커밋)하면 Vercel이 1분에서 2분 안에 자동으로 웹사이트를 바꾼다. Vercel 관리 화면은 A 계정에서만 보인다. 배포가 실패하면 A에게 알린다.

### 서버 약속 (자세한 건 `docs/설계_A_흐름과_서버약속.md`)

| 번호 | 주소 | 하는 일 | 상태 |
|---|---|---|---|
| 1 | `POST /api/start` | 직군·문진표 받고 익명 번호와 시나리오(정답 빼고) 돌려줌 | ✅ 작동 |

**1. 해시체인 (`hashchain.py`): 무엇을 하는 코드인가요**

- 게임 결과를 적는 장부에 **고치면 들키는 도장**을 찍는 코드예요. 기록마다 **바로 앞 기록의 지문**을 함께 묶어서 지문을 만들어요. 중간 기록을 고치면 그 기록의 지문이 달라지고, 뒤 기록에 적힌 "앞 지문"과도 안 맞아서 바로 들켜요
- 함수 3개 (+ 보조 2개):

| 함수 | 하는 일 |
|---|---|
| `build_entry(prev_entry, record)` | 새 기록 한 줄을 만들고 지문을 찍어요. `prev_entry`는 바로 앞 기록(첫 기록이면 `None`) |
| `verify_chain(entries)` | 장부 전체를 처음부터 다시 계산해서 도장이 맞는지 검사해요 |
| `compute_hash(seq, prev_hash, record, created_at)` | 지문 하나를 계산해요 |
| `canonical(obj)` | 같은 내용이면 항상 같은 글자가 되게 정리해요 (키 순서 정렬, 공백 없음, 한글 그대로) |

- 지문은 `SHA-256( canonical({seq, prev_hash, record, created_at}) )`이에요. 첫 기록의 `prev_hash`는 `"0"`을 64개 쓴 값이에요
- `entry` 모양: `{"seq", "prev_hash", "record", "created_at", "hash"}`. `record`는 서버가 만든 10칸(설계 A의 "장부 한 줄에 넣을 것")이 그대로 들어가요
- `verify_chain`이 알려 주는 것:

| 상황 | 돌려주는 값 |
|---|---|
| 이상 없음 | `{"ok": True, "count": 개수}` |
| 기록 내용이 바뀜 | `{"ok": False, "broken_seq": 번호, "reason": "기록 내용이 바뀜 (변조)"}` |
| 기록이 중간에서 삭제·삽입됨 | `... "reason": "순번이 끊김 (기록 삭제·삽입 의심)"` |
| 순서가 바뀜 | `... "reason": "앞 기록의 지문이 안 맞음"` |

- ⚠️ **변조를 막는 것이 아니라 들키게 하는 것**이에요. 작품설명서에는 "위변조 탐지·검증"이라고 써요
- ⚠️ **맨 끝 기록들을 통째로 지우면 못 잡아요.** 또 서버 관리자가 장부를 처음부터 다시 계산해서 통째로 바꾸는 것도 못 막아요. 보완책(마지막 지문·개수를 따로 저장, 서버만 아는 비밀 열쇠 HMAC)은 **예정**이고 아직 안 만들었어요

**2. 장부 저장 (`ledger.py`): 무엇을 하는 코드인가요**

| 함수 | 하는 일 |
|---|---|
| `append_record(record: dict) -> dict` | 마지막 기록을 읽고 `build_entry`로 새 기록을 만들어 DB에 저장한 뒤, 저장된 `entry`를 돌려줘요 |
| `load_entries() -> list` | 모든 기록을 `seq` 순서대로 돌려줘요 (`verify_chain`과 통계 계산에 씀) |

- **어디에 저장하나:** 환경 변수 `DATABASE_URL`이 **있으면** Neon Postgres, **없으면** SQLite 파일을 써요 (파일 이름은 환경 변수 `LEDGER_SQLITE`, 없으면 `ledger_test.db`). 그래서 같은 코드를 Colab에서 시험하고 Vercel에서는 진짜 DB로 돌릴 수 있어요
- **테이블 하나:**

```sql
CREATE TABLE IF NOT EXISTS ledger (
    seq        BIGINT PRIMARY KEY,
    prev_hash  TEXT NOT NULL,
    record     TEXT NOT NULL,
    created_at TEXT NOT NULL,
    hash       TEXT NOT NULL UNIQUE
)
```

- **지켜야 할 약속 (바꾸면 장부 검사가 틀어져요):**
  - `record`는 **JSONB가 아니라 TEXT**로 저장해요. JSONB는 키 순서와 공백을 바꿔 저장해서, 다시 계산한 지문이 달라져요
  - `created_at`도 날짜 형식이 아니라 **글자** 그대로 저장해요 (지문 계산에 쓴 글자와 같아야 해요)
  - 두 요청이 동시에 같은 `seq`를 쓰면 한쪽이 저장에 실패해요. 코드가 **마지막 기록을 다시 읽고 최대 8번 재시도**해요
  - 호출할 때마다 DB 연결을 열고 닫아요 (Vercel처럼 요청 때만 켜지는 서버에 맞춤)
- **시험 결과 (Colab, SQLite, 10/25):**

| 시험 | 결과 |
|---|---|
| 5건 저장 후 검증 | `ok: True, count: 5` |
| DB에서 2번 기록을 몰래 수정 | `broken_seq: 2`, "기록 내용이 바뀜 (변조)" |
| DB에서 3번 기록을 삭제 | `broken_seq: 3`, "순번이 끊김" |
| 5명이 동시에 8건씩 저장 | 40건 저장, 오류 없음, 체인 정상 |

- 공모전 규정상 **AI 활용내역을 빠뜨리면 심사에서 제외되거나 상을 받아도 취소될 수 있다.** 작품설명서와 포스터에 AI 활용내역을 적어야 하고, 그 근거가 구글 시트의 **AI활용 기록표**다
- **Claude로 작업한 날은 그날 바로** 기록표에 한 줄 이상 적는다. 칸: 날짜 / 쓴 사람 / AI 도구 / 단계 / 범위 / 고친 부분 / 확인 방법
- 가장 중요한 칸은 **"고친 부분"과 "확인 방법"**이다. 심사는 AI를 얼마나 썼는지보다 **사람이 직접 판단·수정·검증한 내용**을 본다. "AI가 만든 코드를 직접 실행해 결과 확인", "제안 중 ○○는 팀 결정에 맞게 바꿈"처럼 구체적으로
- **지난 작업도 빠진 게 있으면 지금 채운다.** 예: 해시체인 노트북·코드 작성, 시나리오·문진표·화면 설계, 이메일 배점표 작성 등 AI와 함께 한 작업
- **AI의 오류나 놓친 점을 찾아 바로잡은 것은 꼭 적는다.** 예: "AI가 추천한 ○○가 틀린 것을 질문으로 짚어 △△로 변경", "AI 구현이 설계와 다른 것을 직접 발견해 수정". 사람이 검증했다는 가장 강한 근거다
- 자기가 한 작업은 **자기 이름으로 직접** 적는다 (다른 사람이 대신 적지 않는다)
- Claude 대화는 **절대 지우지 않는다** (심사 종료 후 3개월 보관). 대화 끝에 Claude가 정리해 주는 "AI 활용내역"을 그대로 옮기면 쉽다
- 진행 상황 시트에서 **자기가 검수자인 줄**은 직접 확인해 보고 **검수 결과** 칸을 채운다 (예: "배포 사이트에서 직접 플레이, 결과 화면까지 정상")

## 5. 왜 이렇게 만들었나

### 결과지 양식(JSON)과 샘플: 왜 만들었나 (가장 중요)

**JSON = 건강검진 결과지 양식.** 어느 병원이든 결과지 모양이 같듯, 링크 검사든 이메일 검사든 결과를 같은 6칸으로 적는다. 그래야 세 명이 따로 만들어도 연결된다.

```
A(링크 검사) ─┐
              ├─ 결과지(JSON) ──→ B가 화면(게임 해설)에 보여줌
B(메일 검사) ─┘               └→ C가 장부(해시체인 기록)에 저장
```

| 칸 | 결과지로 치면 | 뜻 |
|---|---|---|
| `type` | 무슨 검사 | `url` 또는 `email` |
| `input` | 누구 검사 | 검사한 링크 주소 또는 메일 파일 이름 |
| `score` | 종합 판정 | 위험 점수 0에서 100. **반드시 `reasons`의 `points` 합계** |
| `model_probability` | (추가 소견) | AI 모델의 피싱 확률 0에서 1. 모델이 없으면 `null` |
| `reasons` | 항목별 수치·소견 | 이유 목록. 각각 `factor`(이름) / `points`(점수) / `text`(설명 문장) |
| `unavailable` | 미실시 항목 | 확인 못 한 항목 이름 (`whois` = 도메인 생성일 조회 실패, `spf` = 메일 검사 결과 없음, `auth` = 이메일 헤더에 인증 결과가 없음). 0점 처리하지 않는다 |

**샘플 = 결과지 견본.** 검사기가 완성되기 전에 견본을 먼저 나눠 주면, B는 견본으로 화면을, C는 견본으로 저장 기능을 먼저 만들 수 있다.

| 파일 | 점수 | 이유 | 보여주는 상황 | 만든 방법 |
|---|---|---|---|---|
| `url_dangerous.json` | 75 | 도메인 유사 35 / 생성일 30 / 키워드 10 | 유명 이름(naver)을 따라 한 위험 링크, 모델 확률 있음 | 손으로 작성. 0.91은 **가짜 예시 값** |
| `url_whois_fail.json` | 60 | 도메인 유사 35 / 기관명 불일치 15 / URL 구조 10 | 정부기관(gov) 사칭, 생성일 조회 실패 → `unavailable: ["whois"]` | 노트북 셀 7에서 10이 생성 |
| `email_spoof.json` | 70 | SPF 실패 40 / 보낸 사람 불일치 30 | 인사팀 사칭 위조 메일, 모델 없음 → `null` | `email_practice.ipynb`가 생성. **옛 배점이라 새 배점으로 다시 만들 예정** |

### 탐지 엔진 실험과 보완

Colab(실험실)에서 먼저 시험해 보고 웹으로 옮겼다. 정부기관 사칭 링크가 처음엔 **0점**(주소 앞부분에 숨긴 이름을 못 찾음), 텔레그램 사칭이 **20점**(하이픈에 붙은 철자 위조를 못 찾음)이었는데, 보완해서 지금은 정부 사칭 **60점**, 텔레그램 사칭 **55점**, 진짜 사이트(구글, 정부24, 네이버 로그인, 카카오) **0점**이다.

링크 배점(초안): 도메인 유사 35 / 생성일 30 / 기관명 불일치 15 / 키워드 10 / URL 구조 10 = 100.

이메일 배점은 B가 10/24에 확정했다: DMARC 28 / SPF 17 / DKIM 0 / 표시 이름 위장 17 / 답장 주소 불일치 17 / 첨부 파일 위험 11 / 긴급성·압박 문구 10 = 100. 옛 임시값의 "보낸 사람 불일치(From과 Reply-To의 도메인이 다름)"는 지금 **"답장 주소 불일치"**라는 이름이다.

### 게임 흐름과 채점 (팀 결정)

1. 시작: 직군 선택 → 2. 문진표 4개(Q1 자신감 1점에서 5점) → 3. 시나리오마다 **행동 3개 중 하나** 선택 → 4. 해설("속았어요 / 잘 막았어요 / 정상 메시지였어요 / 과잉 의심") + 수상한 점(clues) + 탐지 엔진 분석 → 5. 결과("자신 있다고 하셨지만 이번엔 2번 속으셨어요", 약한 유형, 팁)

| 시나리오 | `click` 링크·첨부 열기 | `call` 메시지에 적힌 번호로 전화 | `official` 공식 경로로 확인 |
|---|---|---|---|
| 피싱 | 오답 | 오답 (보이스피싱 함정) | 정답 |
| 정상 | 정답 | 정답 | 정답, 단 과잉 의심으로 따로 집계 |

보안 원칙: 정답·해설은 화면에 **미리 보내지 않고**, 채점은 **서버가** 한다. 입력은 정해진 값만 받는다. 링크에는 **접속하지 않는다.**

- 새 파일을 만들려다 **기존 파일 이름을 바꿈** (Rename) → 새 파일은 Add file → Create new file로

- Colab을 다시 열면 **셀 1부터 다시 실행**해야 함 (설치가 초기화됨)
- 커밋 메시지를 안 적으면 `Add files via upload`가 자동으로 붙음
- 폴더 이름을 `docs`가 아니라 `doc`으로 만듦 → README의 폴더 이름과 똑같이
- 폴더는 저절로 안 생긴다. 새 파일 이름 칸에 `api/index.py`처럼 **`/`를 넣어야** 폴더가 생긴다
- Colab의 "`.py`로 다운로드"는 **시험 코드까지** 같이 들어간다 → 서버용 `.py`에는 함수만 남기기
- 노트북 파일(`.ipynb`)의 이름만 `.py`로 바꾸면 안 된다 (안에 노트북 내용이 그대로 들어 있음)
- `main`에 올리면 웹사이트가 바로 바뀐다. 서버 코드는 올리기 전에 한 번 더 확인
