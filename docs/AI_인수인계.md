## 0. AI에게: 이 대화에서 지켜야 할 규칙

너는 지금부터 보안 캡스톤 프로젝트 "캐치피싱"을 돕는다. 아래 내용을 모두 기억한 채로 대화해 줘.

1. **나는 완전 초보야.** GitHub, Colab, 파이썬 모두 처음이야. 초등학생에게 설명하듯 버튼 위치까지 하나씩 알려 주고, "무엇을"과 함께 **"왜"**를 꼭 설명해 줘.
2. **코드는 셀(조각) 하나씩** 줘. 코드 줄 아래에 `# 하는 일:` / `# 이유:` / `# 참고:` 형식으로 각주를 달아 줘. 셀마다 **"나와야 할 결과 | 맞는지"** 표를 붙여 줘. 내가 결과를 캡처해서 보내면 그 표와 대조해 확인해 줘.
3. **녹화 포인트는 그 단계를 하는 바로 그때** 알려 줘 (마지막에 몰아서 X). 형식: `🎬 녹화 | 파일명(예: 1019_시나리오설계.mp4) | 장면 | 길이(10~40초) | 쓰임(초기/중기/완성)`. API 키·이메일 주소·비밀번호·개인정보가 화면에 나오면 주의를 줘.
4. **매 답변 끝에 AI 활용내역**을 `도구 / 목적 / 활용 범위` 형식으로 정리해 줘. 대화가 끝날 때는 아래 6번의 기록표 칸 형식으로 한 줄 정리해 줘.
5. 팀이 같이 정해야 할 것(배점, 기준, 직군 목록 등)은 **네가 정하지 말고** "팀 논의 포인트"로 표시해 줘. 초안을 제안하는 건 괜찮아.
6. 피싱 링크는 **분석만 하고 접속하지 않는다.** 연습용 주소는 `.example`을 쓴다. 실제 수집한 피싱 데이터·개인정보·API 키는 저장소에 올리지 않는다.
7. 팀원들은 시간을 맞추기 어려워. "누가 언제까지 해 줘야 진행된다"는 계획은 짜지 마.
8. 아래 "칸 이름 사전"의 이름을 그대로 써 줘. 바꾸고 싶으면 바꾸자고 **제안만** 하고, 바꾼 이름은 따로 표시해 줘.

## 1. 프로젝트 한눈에 보기

- **작품명:** AI 기반 피싱 탐지 및 기업 보안 교육 체험 플랫폼 "캐치피싱(CatchPhish)"
- **팀:** Phish&Chips (배화여자대학교 소프트웨어공학과 3학년 3명), 지도교수 김현우, 산업체 ㈜푸르고 (산업체 미팅 일정은 아직 미정)
- **한 줄 요약:** 회사 직원이 가짜 메일·문자·링크가 나오는 **시나리오 게임**을 하고, 속았을 때 **AI 탐지 엔진이 "왜 위험했는지" 설명**하며, 기록은 **해시체인으로 위변조를 막아 저장**하고, 회사는 **직군별로 어떤 피싱에 약한지** 통계로 보는 웹 프로그램

### 신청서에 약속한 수행 방법 (신청서는 수정 불가)

1. 파이썬 머신러닝 기반 URL·이메일 피싱 판정 + 요소별 위험도 점수 분해
2. 이메일 헤더(SPF/DKIM/DMARC) 검증 + SHA-256 해시체인 기반 무결성 증적 로그
3. 탐지 엔진과 연동한 시나리오 게임 → 기업용 보안 교육 플랫폼
4. 체험 결과 DB 축적 → 직군·시나리오별 오답률, 취약 패턴 집계
5. 집계 결과 기반 개인별 맞춤 피드백
- 신청서의 결과물: 캐치피싱 프로그램, 캐치피싱 활용 가이드
- 신청서의 활용 기술(안): Python, scikit-learn, dnspython, hashlib, Flask/FastAPI, PostgreSQL

### 결과지 양식(JSON)과 샘플: 왜 만들었나 (가장 중요)

**JSON = 건강검진 결과지 양식.** 어느 병원이든 결과지 모양이 같듯, 링크 검사든 이메일 검사든 결과를 같은 6칸으로 적는다. 그래야 세 명이 따로 만들어도 연결된다.

```
A(링크 검사) ─┐
              ├─ 결과지(JSON) ──→ B가 화면(게임 해설)에 보여줌
B(메일 검사) ─┘               └→ C가 장부(해시체인 기록)에 저장
```

| 칸 | 결과지로 치면 | 뜻 |
|---|---|---|
| `type` | 무슨 검사 | `url` 또는 `email` |
| `input` | 누구 검사 | 검사한 링크 주소 또는 메일 파일 이름 |
| `score` | 종합 판정 | 위험 점수 0~100. **반드시 `reasons`의 `points` 합계** |
| `model_probability` | (추가 소견) | AI 모델의 피싱 확률 0~1. 모델이 없으면 `null` |
| `reasons` | 항목별 수치·소견 | 이유 목록. 각각 `factor`(이름) / `points`(점수) / `text`(설명 문장) |
| `unavailable` | 미실시 항목 | 확인 못 한 항목 이름 (`whois` = 도메인 생성일 조회 실패, `spf` = 메일 검사 결과 없음). 0점 처리하지 않는다 |

**샘플 = 결과지 견본.** 검사기가 완성되기 전에 견본을 먼저 나눠 주면, B는 견본으로 화면을, C는 견본으로 저장 기능을 먼저 만들 수 있다.

| 파일 | 점수 | 이유 | 보여주는 상황 | 만든 방법 |
|---|---|---|---|---|
| `url_dangerous.json` | 75 | 도메인 유사 35 / 생성일 30 / 키워드 10 | 유명 이름(naver)을 따라 한 위험 링크, 모델 확률 있음 | 손으로 작성. 0.91은 **가짜 예시 값** |
| `url_whois_fail.json` | 60 | 도메인 유사 35 / 기관명 불일치 15 / URL 구조 10 | 정부기관(gov) 사칭, 생성일 조회 실패 → `unavailable: ["whois"]` | 노트북 셀 7~10이 생성 |
| `email_spoof.json` | 70 | SPF 실패 40 / 보낸 사람 불일치 30 | 인사팀 사칭 위조 메일, 모델 없음 → `null` | `email_practice.ipynb`가 생성 |

### Colab 실험: 왜 했나

Colab은 **실험실**이다. 웹사이트를 짓기 전에 검사 방법이 실제로 위험한 링크를 잡는지 시험했다(요리 대회 전 레시피 시험). 실험 중 정부기관 사칭 링크가 **0점**으로 나오는 구멍(주소 앞부분에 숨긴 이름을 못 찾음)을 발견해 보완했고, 지금은 **사칭 링크 60점, 진짜 정부 사이트(gov.kr, minwon.go.kr) 0점**으로 구분된다. 샘플 2·3은 손으로 쓰지 않고 검사기가 직접 만든 결과라서 양식과 실제 결과가 항상 같다.

`url_practice.ipynb` 셀 구성: 1 설치 / 2~4 주소 나누기·글자 차이·생성일 조회 연습 / 5 `analyze_url_sample` (도메인 유사·키워드·생성일) / 6 진짜·가짜 비교 / 7 샘플 2 주소 → 0점(문제 발견) / 8 `analyze_url_v2` (앞부분 이름·기관명 불일치·URL 구조 추가) / 9 샘플 2 생성 + `assert` 확인 / 10 파일 저장

`email_practice.ipynb` 셀 구성: 1 가짜 메일 읽기 / 2 `analyze_email_sample` (SPF 실패·보낸 사람 불일치) / 3 샘플 3 생성 + 정상 메일 0점 확인 / 4 파일 저장. 지금은 메일 서버가 적어 둔 검사 결과를 읽기만 하고, 직접 DNS 조회 검증(dnspython)은 다음 단계.

| 유형 | 핵심 | 탐지 엔진 대응 | 상태 |
|---|---|---|---|
| A. 기관·기업 사칭 | 권위 이용 | 기관명 불일치, 메일 보낸 사람 불일치 | 있음 |
| B. 도메인 위조 | 진짜와 비슷한 주소 | 도메인 유사, 생성일 | 있음 |
| C. 심리적 압박 | 슬픔·공포·긴급함 | 긴급성 키워드("즉시, 벌금, 별세, 당첨") | **없음 → 팀 논의** |
| D. 연쇄형 | 여러 단계로 신뢰 쌓기 | 시나리오 게임 스토리로 구현 | 게임에서 |

### 게임 흐름 (결정됨)

1. 직원이 링크로 접속 → 안내("평가가 아니며 결과는 익명으로 모입니다")
2. **문진표:** 습관·자신감 질문 3~4개 + 직군 선택. 이름은 묻지 않고 **익명 번호**를 준다.
3. **게임:** 회사에서 온 것 같은 메일·문자·링크가 뜬다. **행동 3개 중 하나**를 고른다 (링크를 누른다 / 전화로 확인한다 / 공식 경로로 직접 확인한다).
4. 서버가 탐지 엔진으로 분석 → **"당했습니다/안전합니다" + 위험 점수와 이유(reasons)**가 해설로 나옴 → 기록 저장
5. **결과:** "자신 있다고 하셨지만 이번엔 2번 속으셨어요" + 취약 유형 + 습관 교정 팁 (자가평가 vs 실제 차이 = 교육성과 근거)
6. **링크 직접 검사:** 의심 링크를 붙여 넣으면 바로 점수와 이유
7. **관리자(회사 담당자):** 회사 코드로 입장(로그인 없음, 팀 합의 필요) → 직군별 오답률, 많이 속은 유형, 자가평가와 실제의 차이(개인은 안 보임) → **기록 검사 버튼**으로 장부 위변조 여부 확인

### 시나리오 설계 원칙 (너무 쉬운 게임 방지)

- 사례조사 원문 문구를 바탕으로 **진짜와 헷갈릴 만큼 현실적으로**
- **정상 메시지도 섞기** (무조건 의심하면 만점이 되지 않게)
- 직군별 시나리오 (인사: 연말정산 / 재무: 송금 요청 / 개발: 계정 보안 알림 등)
- 유형 D처럼 여러 단계로 이어지는 시나리오 포함
- 교내 전시회용은 나중에 더 쉽게 따로 만든다

### 만드는 방식 (초안, 팀 확정 필요)

GitHub Codespaces(브라우저에서 코딩) / Flask 서버 / SQLite DB (신청서의 PostgreSQL은 "안"이었으므로 변경 가능, 작품설명서에 "확대 시 전환 가능"으로 기재) / 화면은 기본 HTML·JS / 무료 호스팅 배포 / 브랜치 없이 main에 바로 저장 / 저장소 공개 유지
