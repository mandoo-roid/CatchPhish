## 0. AI에게: 이 대화에서 지켜야 할 규칙

너는 지금부터 보안 캡스톤 프로젝트 "캐치피싱"을 돕는다. 아래 내용을 모두 기억한 채로 대화해 줘.

1. **나는 초보야.** 버튼 위치까지 하나씩 알려 주고, "무엇을"과 함께 **"왜"**를 꼭 설명해 줘.
2. **코드는 조각 하나씩** 줘. 코드 줄 아래에 `# 하는 일:` / `# 이유:` / `# 참고:` 각주를 달고, **"나와야 할 결과 | 맞는지"** 표를 붙여 줘.
3. 팀이 같이 정해야 할 것(배점, 기준, 화면 구조 등)은 **네가 정하지 말고** "팀 논의 포인트"로 표시해 줘. 초안 제안은 괜찮아.
4. **사실이 아닌 내용은 넣지 않는다.** 숫자는 이 파일에 있는 값만 쓴다. 모르면 "확인 필요"라고 한다.
5. 피싱 링크는 **분석만 하고 접속하지 않는다.** 연습용 주소는 `.example`, 전화번호는 가짜 번호만. 실제 피싱 데이터·개인정보·API 키는 저장소에 올리지 않는다.
6. "누가 언제까지 해 줘야 진행된다"는 계획은 짜지 마.
7. 아래 "칸 이름 사전"의 이름을 그대로 써 줘. 바꾸고 싶으면 **제안만** 해 줘.
8. `main`에 저장하면 **웹사이트가 바로 바뀐다**(Vercel 자동 배포). 서버 코드를 고치는 안내를 할 때는 올리기 전에 확인할 점과 "A에게 단톡으로 먼저 알리기"를 안내해 줘.
9. 파일을 고쳐 줄 때는 **커밋 문구도 함께** 알려 줘. 형식: `[담당] 무엇을 했는지`. 여러 파일이면 파일별로, 올리는 순서도 함께.

## 📢 팀 공지

### 11/09 (A)

**1. 방향 (예빈과 수업 때 이야기한 것)**
- 「내일의 솔루션」 제출 작업물을 그대로 이어 가되, **회사뿐 아니라 학생·일반인도 교육받을 수 있게** 업그레이드한다
- 기업 교육(실용성)은 그대로 살리고, 관람객도 즐길 수 있는 **게임을 추가**한다
- 지금 체험이 시험처럼 느껴지고 진부하다 → **실제로 메일·문자를 받은 것처럼** 생동감 있게 바꾼다

**2. 화면 구조 (A 제안, 팀 확인 필요)**

```
[시작하기] → 개인용 / 기관용

기관용(직원):   기관 코드 → 체험 → 해설 → 다시 도전 → 비교   (게임 없음)
기관용(담당자): 통계 화면 (지금 관리자 화면)

개인용(학생·일반): 체험 → 훈련(게임) → 다시 체험 → 비교
                + [자유 훈련]: 게임만, 순위표 (전시회 관람객용)
```

- **기관용에는 게임을 넣지 않는다.** 기관이 직원 교육을 게임으로 하지 않고, 속도 경쟁은 나이가 많은 직원에게 불리하다
- **게임은 속도보다 정확성.** 카드 짝맞추기처럼 속도와 상관없는 게임을 기본으로, 스피드 퀴즈는 자유 훈련 순위용으로만 (검토)
- **게임의 교육 효과 입증:** 게임 앞뒤 체험의 결과를 비교한다(막은 피싱 / 처리한 업무). 앞뒤 체험은 문제 세트 A·B를 무작위로 바꿔 내서 난이도 차이를 줄인다 (검토)
- 게임 점수는 체험 장부(해시체인)와 관리자 통계에 **섞지 않는다**

**3. 체험을 생동감 있게 (교수님 제안, 검토 중)**
- 진짜 메일·문자를 받은 것처럼 화면을 구성하고, 선택하면 **내 선택으로 무슨 일이 일어났는지 애니메이션으로 바로** 보여 주기
- 검토 의견: 결과 장면은 시나리오별이 아니라 **결과 유형별 템플릿**(돈 빠져나감 / 계정 탈취 / 앱 설치·정보 유출 / 막았음 / 정상 처리 / 업무 지연)으로 만들어 재사용. **정상 메시지를 멈췄을 때의 결과(업무 지연)도** 보여 줘야 과잉 의심이 늘지 않는다. 장면 뒤에는 꼭 해설
- B가 11/09 올린 **선택 미리보기**(아래 4번)가 이 방향의 첫 단계다

## 5. 약속과 설계 요약 (계속 쓰는 것)

### 결과지 양식 (JSON 6칸)

| 칸 | 뜻 |
|---|---|
| `type` | `url` 또는 `email` |
| `input` | 검사한 링크 주소 또는 메일 파일 이름 |
| `score` | 위험 점수 0~100. **반드시 `reasons`의 `points` 합계** |
| `model_probability` | AI 모델의 피싱 확률 0~1. 없으면 `null` |
| `reasons` | 이유 목록. 각각 `factor` / `points` / `text` |
| `unavailable` | 확인 못 한 항목 (`whois`, `spf`, `auth`). 0점 처리하지 않는다 |

### 탐지 엔진 배점

- **링크:** 도메인 유사 35 / 생성일 30일 미만 30 / 기관명 불일치 15 / 의심 키워드 10 / URL 구조 10. 생성일 조회 실패는 "확인하지 못한 항목"으로 표시. 판정 구간 60 이상 위험, 30 이상 주의
- **이메일:** DMARC 28 / SPF 17 / DKIM 0 / 표시 이름 위장 17 / 답장 주소 불일치 17 / 첨부 위험 11 / 압박 문구 10. 헤더에 적힌 인증 결과(`auth_results`)를 읽어 점수로 바꾼다. DKIM 0점 이유: 정상 메일도 서명이 자주 깨져 오탐이 나기 때문. 카드에 `dkim=fail`은 쓰지 않는다
- 문자 해설에는 본문 압박 문구를 따로 보여 주고, 링크 점수에는 넣지 않는다
- 새 시나리오를 만들면 링크를 `/check`에 넣어 점수를 확인한다

### AI 모델 (URL 피싱 확률)

- **데이터:** PhiUSIIL Phishing URL (UCI 967, Arvind Prasad·Shalini Chandra 2024, DOI https://doi.org/10.1016/j.cose.2023.103545, CC BY 4.0). 저장소에 올리지 않는다
- **모델:** 주소 모양 특징 9개, 로지스틱 회귀 (Colab 학습, 서버에는 숫자만 `url_model.json`)
- **성능 (시험용 47,159개):** 정확도 76.5%, 정밀도 94%, 재현율 48%
- **쓰는 방법:** 위험 점수에 더하지 않고, 피싱 확률 60% 이상일 때만 참고 표시. 아래는 "주소 모양만으로는 구별하기 어려워요"
- 특징·단어 목록을 바꾸면 노트북에서 다시 학습하고 `url_model.json`도 바꿔야 한다

### 장부 약속 (C, 바꾸면 기록 검사가 틀어짐)

- 사이트에서 쓰는 것: `ledger_v2.py`·`hashchain_v2.py`. 고치면 바로 기록 저장이 바뀐다. Colab SQLite로 먼저 시험하고, 올리기 전에 A에게 알린다
- 테이블 `ledger(seq, prev_hash, record, created_at, hash)`. `record`와 `created_at`은 **글자** 그대로 저장
- 지문 = SHA-256 (환경 변수 `HASH_SECRET`이 있으면 HMAC-SHA256). 첫 기록의 `prev_hash`는 `"0"` 64개
- `ledger_head` 표로 **끝 기록 삭제**도 잡는다. **장부를 비울 때는 `ledger`와 `ledger_head`를 둘 다** 비운다. 열쇠를 바꾸면 그 전 기록은 전부 "변조"로 나온다
- 해시체인은 변조를 **막는 것이 아니라 들키게 하는 것** → "위변조 탐지·검증"이라고 쓴다
- 알려진 한계: 열쇠 노출 시 보호가 약해짐, DB와 Vercel 설정을 둘 다 가진 사람은 못 막음, 저장 실패한 기록은 장부에서 빠짐
- **장부 한 줄:** `anon_id`, `job`, `self_check`, `scenario_id`, `case_type`, `is_phishing`, `choice`, `is_correct`, `over_suspicion`, `analysis` (+ 2회차 `round`, 연쇄형 `stopped_step`)
