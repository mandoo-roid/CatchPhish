## 2. 칸 설명

| 칸 | 넣는 값 | 규칙 |
|---|---|---|
| `scenario_id` | P01, S02B … | 위 번호 그대로 |
| `audience` | `personal` / `org` | **새 이름표** |
| `set` | `"A"` / `"B"` | **새 이름표** |
| `pair` | 1, 2, 3 … (숫자) | **새 이름표.** 쌍둥이끼리 같은 숫자 |
| `channel` | `sms` / `email` | |
| `job_group` | 개인용은 `common`, 직군 카드는 `hr`·`finance`·`sales`·`dev`·`office` | |
| `is_phishing` | `true` / `false` | |
| `case_type` | `A+C`처럼 공백 없이, 정상은 `null` | A 기관 사칭, B 도메인 위조, C 심리 압박, D 연쇄형 |
| `sender` | 화면에 보일 보낸 곳 | 번호·주소는 가짜만 (`010-0000-0000`, `02-0000-0000`, `.example`) |
| `from`·`reply_to`·`auth_results` | 메일만 | 아래 4번 |
| `subject` | 메일 제목, 문자는 `null` | |
| `body` | 본문 | **단서는 반드시 본문 안에** (해설에서 짚을 수 있게) |
| `link` / `attachment` | 없으면 `null` | 링크는 `.example`만 |
| `clues` | `factor`(이름) + `text`(설명) 목록 | 쌍둥이끼리 **개수 같게** |
| `explanation` | 긴 해설 | 정상 카드는 "왜 정상인지"(요구하는 행동이 안전한 이유)를 꼭 |
| `explanation_short` | 해설 화면 맨 위 한 줄 | |
| `choice_labels` | `click`·`call`·`official` 문구 | 아래 3번 |
| `consequence` | (피싱, 선택) 속았을 때 피해 `title`·`detail` | |
| `source` | 바탕이 된 자료 | 가상이면 "가상 구성" |

## 3. 선택지 문구 규칙 (가장 중요)

- **세 개 모두 "확인한다"**, 확인하는 길만 다르게
  - `click`: 메시지 속 링크·첨부로 확인
  - `call`: 메시지에 적힌 번호·답장으로 확인
  - `official`: 공식 앱·포털·대표번호로 직접 확인
- "의심", "멈춘다", "수상한" 같은 정답 냄새 나는 말 빼기
- 세 문장 길이 비슷하게
- 화면에서 순서는 A가 섞어요

## 4. 메일 카드 헤더 (B 포렌식 담당)

| 칸 | 뜻 | 피싱 예 | 정상 예 |
|---|---|---|---|
| `from` | 보낸 사람 (표시 이름 + 실제 주소) | `OO대학교 포털 <noreply@univ-portal-notice.example>` | `OO대학교 포털 <noreply@univ.example>` |
| `reply_to` | 답장이 가는 주소 | 보낸 주소와 다르게 할 수 있음 | 보통 `null` |
| `auth_results` | 메일 인증 결과 | 위조면 `spf=fail ...; dkim=none; dmarc=fail` / 비슷한 주소를 직접 등록했으면 `pass` | `spf=pass ...; dkim=pass; dmarc=pass` |

**더 어렵게:** 표시 이름은 학교·회사인데 실제 주소만 비슷하게 바꾼 메일 (화면에서는 이름만 보이고, 눌러야 주소가 보여요). 인증까지 통과하게 만들면 "인증 통과 = 안전"이 아니라는 걸 배워요.
