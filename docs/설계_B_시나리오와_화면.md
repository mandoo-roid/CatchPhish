# 설계 B: 시나리오와 화면 (초안)

담당: B / 상태: 작성 중 (칸 이름은 임시, 맞춰 보기에서 확정)

## 1. 시나리오 카드 양식

게임에 나오는 메일·문자·링크 한 개를 아래 칸으로 적는다. 점수는 카드에 적지 않는다(점수는 탐지 엔진이 계산).

| 칸 이름(임시) | 뜻 | 비고 |
|---|---|---|
| scenario_id | 카드 번호 (S01~) | |
| channel | 메시지 종류: email / sms / url | 결과지의 type(url / email)과 겹치지 않게 channel로 함. A의 설계와 같은 이름 (팀 확인 대기) || job_group | common / hr / finance / sales / dev / office | 직군 목록은 임시(산업체 미팅 후 조정) |
| is_phishing | 피싱이면 true, 정상이면 false | |
| job_group | common / hr / finance / sales / dev / office | 직군 목록은 임시(산업체 미팅 후 조정). 직원의 직군(A 설계의 job)과 뜻이 달라서 이름을 다르게 둠. 칸 이름 사전에 추가 요청 |
| sender | 보낸 사람 (표시 이름과 주소 또는 번호) | 연습용 .example 주소, 가짜 번호만 사용 |
| subject | 제목 (문자는 빈칸) | |
| body | 본문 | 실제 회사·사람 이름, 진짜 번호 쓰지 않기 |
| link | 본문 속 링크 (없으면 빈칸) | 접속하지 않고 분석만 함 |
| attachment | 첨부 파일 이름 (없으면 빈칸) | 이번 초안에서 추가 제안. 팀 확인 필요 |
| clues | 수상한 점 목록 (이름 + 설명 문장) | A의 reasons와 비슷한 모양 |
| explanation | 정답 해설 (쉬운 말 2~3문장) | |
| source | 참고한 사례 | 사례조사 번호 또는 "가상 구성" |

### 정답 규칙 (팀 결정 10/19)

- 행동 3개: click(링크·첨부 열기) / call(메시지에 적힌 번호로 전화) / official(공식 경로로 직접 확인)
- 피싱: click·call은 오답, official이 정답
- 정상: 모두 정답. 단 official은 "과잉 의심"으로 따로 집계
- 게임 속 가상 회사의 공식 주소는 company.example 로 가정한다

## 3. 문진표 질문

게임을 시작하기 전에 직원이 답하는 질문 4개. 정답이 없고, 게임 결과와 비교하는 데 쓴다.

### 화면에 쓸 안내 문구 (초안)
"정답이 있는 질문이 아닙니다. 평소 모습 그대로 답해 주세요. 답은 익명 번호로만 저장됩니다."

### 질문 양식 (칸 이름은 임시)

| 칸 이름(임시) | 뜻 |
|---|---|
| question_id | 질문 번호 (Q1~) |
| text | 화면에 보이는 질문 문장 |
| answer_type | scale5(1~5점) 또는 choice(하나 고르기) |
| options | 선택지 목록 |
| purpose | 이 답을 어디에 쓰는지 |

### 질문 목록

| 번호 | 질문 | 답 종류 | 선택지 | 쓰임 |
|---|---|---|---|---|
| Q1 | 수상한 메일이나 문자를 받으면 피싱인지 구분할 자신이 있다. | scale5 | 1점(전혀 아니다) ~ 5점(매우 그렇다) | 자가평가 점수와 실제 정답률의 차이 |
| Q2 | 최근 1년 안에 피싱이 의심되는 메일·문자를 받아 본 적이 있나요? | choice | 없다 / 있었지만 그냥 지웠다 / 있었고 링크나 첨부를 열어 본 적이 있다 / 있었고 공식 경로로 확인했다 / 잘 모르겠다 | 경험에 따른 오답률 비교 |
| Q3 | 모르는 링크가 담긴 문자를 받으면 보통 어떻게 하나요? | choice | 링크를 눌러 확인한다 / 문자에 적힌 번호로 전화해 본다 / 공식 앱이나 대표번호로 직접 확인한다 / 무시한다 | 평소 습관과 게임에서 고른 행동(click·call·official)의 차이 |
| Q4 | 최근 1년 안에 정보보안(피싱) 교육을 받은 적이 있나요? | choice | 있다 / 없다 / 기억나지 않는다 | 교육 경험에 따른 결과 비교 |

- Q3의 앞 3개 선택지는 팀이 정한 행동 3개(click / call / official)와 같다. "무시한다"는 게임에 없는 행동이라 4번째로 추가했다.
- 직군(hr, finance, sales, dev, office) 선택은 문진표에 넣을지 시작 화면에 따로 둘지 아직 정하지 않았다.

## 6. 칸 이름 대조 (README 결과 형식 기준, 10/19 초안)

A의 결과 형식(README)과 B의 화면·카드 칸 이름을 맞춰 본 표. 칸 이름 사전(AI_인수인계.md)과 A·C 설계 파일과는 아직 대조하지 않았다.

### 6-1. 결과 형식과 화면의 연결

| 결과 칸 | 화면에서 쓰는 곳 | 상태 |
|---|---|---|
| type | 링크 직접 검사(화면 5), 엔진 분석 표 | 일치 |
| input | 화면 5에서 입력한 주소, 링크가 있는 카드의 link | 일치 (이메일 카드는 아래 6-2 참고) |
| score | 해설(화면 3-2), 화면 5 | 일치 |
| model_probability | 아직 화면에 없음 | 확인 필요: 값이 null일 때 문구 |
| reasons (factor / points / text) | 해설(화면 3-2), 화면 5의 표 | 일치 |
| unavailable | 해설, 화면 5의 안내 문구 | 일치. 단 whois, spf 같은 이름은 화면에서 읽기 쉬운 말로 바꿔 보여 줘야 함 |

### 6-2. 어긋날 수 있는 곳

1. 카드의 메시지 종류는 channel로 바꿨다. 결과의 type(url / email)과 이름이 겹치지 않게 하기 위해서이고, A의 설계와 같은 이름이다. (팀 확인 대기)
2. 카드의 clues(factor, text)에는 points가 없어 결과의 reasons(factor, points, text)와 모양이 다르다. 맞출지 팀에서 정한다.
3. 이메일 카드는 헤더 파일이 없어서 엔진(결과의 input = 메일 파일 이름)에 그대로 넣을 수 없다. 헤더 정보를 카드에 넣을지, 이메일은 엔진 분석 없이 해설만 보여 줄지 팀에서 정한다.
4. 직군 코드(hr / finance / sales / dev / office)와 행동 코드(click / call / official)는 팀 결정과 같다.
5. 문진표 답과 게임 결과를 C의 기록 한 줄(익명 번호, 직군, 시나리오 번호, 고른 행동, 맞았는지, 시간 등)에 어떻게 넣을지는 C의 설계 파일과 대조해야 한다.
